# 构建、测试与故障场景

## 已执行的本地验证

本地使用 MinGW GCC 15.2.0 编译，启用 C11、`-Wall -Wextra -Werror -Wpedantic -Wshadow -Wconversion`。四组 C 测试及正常、掉线两条场景已通过。FreeRTOS 适配层通过真实 V11.2.0 头文件与官方 MSVC-MingW 端口头文件的语法/API 检查。

CMake Release 构建与 CTest 的 6 项检查也已在本地通过。Linux sanitizer 由工作流另外执行，运行结果以仓库 Actions 为准。主机测试不构成电池、充电器或柜门硬件验证。

## 测试分组

| 测试 | 主要检查 |
| --- | --- |
| `test_protocol` | CRC 已知向量、公开请求报文、边界数量、异常响应、错误地址/长度/CRC、逐字节分片、粘帧、噪声、最大帧、重试与时钟回绕 |
| `test_domain` | 10000 组确定种子的功率预算约束、低额轮换、完整换电、重复请求、开锁失败、全部阶段超时、温度与过期联锁 |
| `test_storage_update` | 空介质默认配置、损坏副本回退、擦写中断、序列回绕、无效参数、升级偏移/长度、存储读回损坏、I/O 失败及超时 |
| `test_controller` | 多仓预算、门开停充、掉线停充与恢复、升级互斥、事件溢出锁存、零功率命令失败时禁止开锁 |
| `scenario_normal` | 8 秒虚拟时序：归还、取电、升级暂存、预算变更及结果导出 |
| `scenario_fault` | 正常场景中注入单仓通信中断，检查停充与链路恢复 |

测试使用实际模块入口和虚拟端口，不依赖伪造的 FreeRTOS 头文件。C 测试保留断言，Release 构建也不会关闭这些检查。

## 场景时间线

| 时间 | 事件 |
| --- | --- |
| 0 ms | 仓位 1、2 有电池，仓位 1 达到取电条件；开始轮询 |
| 500–800 ms | 向仓位 0 归还电池，再从仓位 1 取出电池，完成一次流程 |
| 2000 ms | 故障场景中仓位 2 停止应答 |
| 4000 ms | 故障场景中仓位 2 恢复应答 |
| 4500–4800 ms | 以两块数据接收镜像，读回确认，期间所有仓位零功率 |
| 5000 ms | 持久化新配置，整柜预算由 800 W 调整为 400 W |
| 8000 ms | 写出完整轨迹与汇总 |

主机按 10 ms 推进控制，每 50 ms 记录一次轨迹，共 161 个采样点。`tools/build.py` 除了检查进程返回值，还解析 JSON 并检查总预算、流程完成、升级状态、停充区间以及故障仓位恢复。

## 故障注入入口

`host_port_t` 提供 `offline[]`、`corrupt_reply`、`unlock_failed`、`output_failed`、`torn_write`、`image_failed`。它们只作用于主机虚拟设备，没有访问物理硬件的副作用。

## 尚未覆盖

- 目标 MCU 编译、FreeRTOS 调度运行、任务栈峰值与实时性测量。
- 串口电气时序、EMC 噪声、DMA 并发、真实 RS485 收发切换。
- 实际功率输出反馈、电池兼容性及硬件保护。
- 真实 Flash 擦写寿命、掉电波形、启动切换和回滚。
- 长时间稳定运行、硬件看门狗、认证与网络安全。

这些事项需要对应硬件与集成环境，不能从纯主机测试推导为已通过。
